# 架构与上游边界

状态：部分已实现。实例、运行时、凭据及图形页面已接入；发行版验证仍在进行。

工作区分为 `core`、`ui` 与 `app`：`core` 处理磁盘状态、下载、进程、npm 元数据、插件兼容和凭据；`ui` 只定义 Slint 页面与事件；`app` 将事件接到异步服务。核心逻辑不依赖 Slint，以便在无图形环境测试。

启动器只管理 Harness，不修改 Harness 源码。安装版本以 npm `@deepseek-ai/dsh@<精确版本>` 为准。启动时使用该安装的 `bin` 入口、实例工作目录及实例专属 `DSH_HOME`。插件操作使用同一版本的 `dsh plugin --profile web`，不得使用系统全局的 `dsh`。

网络来源限定为 Node.js 官方发行索引、npm registry、插件目录和 GitHub 元数据。安装前验证 Node 官方 SHA256 与 npm 包的 integrity。Node 下载使用临时目录；Harness 直接安装在最终实例目录，因为 Windows 上 pnpm 链接不能随目录移动。成功验证后才写入 `instance.json`，因此失败安装不会出现在实例列表。

界面按 HMCL 的导航层级重做，资源文件独立创作。不得复制参考项目的图标、壁纸或角色图。

验收：两个版本同时运行时，入口、工作目录、端口和 `DSH_HOME` 均不串用；停止一个实例不会终止另一个实例。

## 离线使用已安装运行时（已实现）

启动已有实例时，先从本地 `runtimes/node/24.*` 中选择最新且可执行的 Node.js 24 LTS；只有本地不存在有效运行时才查询官方索引并下载。这样网络中断时，已安装实例仍可启动与管理插件。安装新实例仍通过 npm 获取 Harness 精确包版本。验收：官方索引不可达但本地运行时可用时，`ensure_node24` 不发起网络请求。

2026-09-23 在线测试曾在同一进程安装 `0.1.5-rc.3` 与 `0.1.5-rc.2`，分别用独立工作目录、端口和 `DSH_HOME` 启动 Web；复测又发现旧版可能因子包版本漂移而启动失败，见下节。此测试需要访问官方分发站和 npm，默认标记为 ignored。

## Harness 子包版本收敛（计划中）

预发布版的上游依赖使用 `^0.1.5-rc.2` 等范围，pnpm 可能把 `dsh` 主包保持在用户选定的精确版本，却将 `@deepseek-ai/dsh-*` 子包解析到后续 RC。在线复测中 `0.1.5-rc.2` 曾因此在 Web 启动时报缺少 HMR 服务。安装时应依据所选主包的实际依赖，先对同版本的 DSH 家族子包建立精确覆盖；安装后检查完整已装图谱，发现仍漂移的家族包时尝试进一步收敛，不能把未验证的混合版本实例写入列表。独立版本验证应连续通过，而非仅验证命令行 `--version`。

验收：`0.1.5-rc.2` 与 `0.1.5-rc.3` 的 Web 均可启动；各自 DSH 家族子包没有跨实例版本漂移，且停止一个实例不影响另一个。不存在所选精确版本的子包时安装须失败并清理目标目录。

## API 设置保存事务（已实现）

API 页目前只直接编辑已核验的 DeepSeek 官方字段。保存前必须先验证密钥与所有填写的设置，并在内存中生成两个完整 YAML 文档。端点必须是无用户信息、查询和片段的 HTTP(S) 地址。任何验证失败不得修改现有凭据或设置；写入第二个文件失败时要恢复第一个文件，保留原内容。界面应允许显式移除已配置的密钥，留空输入仍表示不修改。未知文档结构不得被覆盖，提示在 Harness 原生设置中处理。

验收：错误端点与异常 YAML 不会部分写入；正确设置保留现有未知字段；清除密钥后界面显示未配置；错误和日志中不出现密钥原文。
