# 文档先行与 Git 工作流

功能状态统一记录在[功能状态与限制](status.md)。本页说明贡献与提交约定。

每项用户可见功能按三个可构建提交进入历史：

1. `docs(dev): ...`：先写行为、上游契约、失败路径和验收条件，在状态页登记设计阶段；
2. `feat:` 或 `fix:`：实现代码和测试，更新状态页并核对实际接线；
3. `docs(user): ...`：补操作步骤、截图说明和排障。

一次提交只覆盖一个可回滚的功能切片。提交前运行适用的格式、测试或文档构建检查；不得提交密钥、实例数据、下载的运行时和生成的书籍。发行版本使用 Git 标签；保留分阶段提交，不将整项功能压成单个提交。

内部重构没有用户行为变化时，可以省去用户文档提交，但必须更新受影响的开发者文档。PR 说明列出设计文档、测试结果和用户文档位置。

撰写文档时，先核对核心代码、应用回调和界面控件，再更新状态页；不要把单次测试结果写成永久能力声明。带日期的核验数据放在[验证记录](verification.md)，用户可见的上游问题放在有核验日期的用户公告。长期文档面向用户与贡献者，避免过程日志和自动化任务分工。
